# Behavioral Cloning on CS2

This project explores behavioral cloning as a method for training an agent to play CS2 (a first-person shooter game) by learning directly from human gameplay.

---

# Motivation

The main motivation for this project is to investigate how complex human gameplay behavior in CS2 can be learned from demonstrations. Behavioral cloning treats gameplay as a supervised learning problem. At each game tick, the agent receives an observation describing the current game state and learns to predict the action taken by a human player in that situation. Rather than explicitly programming rules for aiming, movement, and combat, the goal is to learn these behaviors directly from demonstrations.

FPS gameplay involves a combination of highly reactive decisions: tracking targets, adjusting aim, moving around the map, responding to incoming damage, and deciding when and where to attack. These behaviors are difficult to describe completely using hand-written rules, but human players naturally demonstrate them through gameplay.

Behavioral cloning provides a way to capture these behaviors directly from examples. Instead of explicitly specifying how the agent should aim or move, the model learns the relationship between the game state and the actions chosen by a human player.

## Why CS2

CS2 was chosen as the environment for this project because it provides a rich and relatively accessible environment for collecting gameplay data. There are many existing resources and tools for reverse engineering the game and extracting game-state information directly from system memory. This makes it possible to efficiently collect observations from gameplay without relying solely on visual input.

CS2 also has a popular and relatively simple game mode called Deathmatch. In Deathmatch, players spawn on a relatively small map and fight independently against other players. Compared to the game's main competitive modes, there is much less emphasis on complex tactics and team coordination. The primary behaviors are moving around the map, finding opponents, aiming, and shooting, making Deathmatch a good starting point for experimenting with imitation learning.

The main competitive game modes, on the other hand, are considerably more complex and require significantly more decision-making. Players are divided into two opposing teams and have access to various weapons and utility that can be used to achieve the round objective. Players must coordinate with their teammates and make decisions based on many different factors, such as their teammates' health, available equipment, positions on the map, and the state of the enemy team.

Because information about the enemy team is often incomplete, players also need to infer the enemy team's condition from the information available to them. In addition, players must consider the economic state of their team. For example, they may need to decide whether to attempt to win the current round with their available equipment or save their equipment and resources for the following round.

This project, in its current state, focuses exclusively on imitation learning in the simpler free-for-all Deathmatch mode. The agent's primary objectives are to learn how to navigate the map and aim at other players.

Learning to play the main competitive game modes would be a significantly more challenging problem, especially as a first project in imitation learning. However, if the current approach proves successful, extending the project to more complex game modes would be an interesting direction for future work.

Another aspect of CS2 that makes it particularly interesting for this project is the large amount of gameplay data generated by human players. A player can simply join a server and observe other players, providing a potentially large source of demonstrations. Since game-state information can be extracted directly from the local game process, this data can also be collected more efficiently than if the agent had to rely entirely on screen observations.

There is, however, an important limitation to this approach. CS2 is a client-server game, and the values available from the local game process do not necessarily correspond exactly to the authoritative state maintained by the server. The observations available to the model therefore represent the game's local interpretation of the state rather than a perfect representation of the server-side state. This needs to be taken into account when collecting data and evaluating the resulting agent.

# What Is Recorded From the Game?

For each player, the following data is recorded on every game tick:

- **Bone matrix** - position and orientation for each hitbox bone
- **Eye position**
- **View angles**
- **Player origin**
- **Absolute velocity**
- **Button mask** - which keys are currently pressed
- **Player health**
- **Ammo count**
- **Player status flags**
  - Is reloading
  - Is airborne
  - Is ducking

---

# Processing the Data

## What Does a Single Processed Frame Look Like?

Each processed game tick is represented by three observations and one action label:

1. **Self observation** - the state of the player being controlled
2. **Enemy observation** - the visual/geometric information about visible enemies
3. **Damage observation** - information about damage recently received by the player
4. **Player action** - the action taken by the human player on that tick

## Self Observation

The bot's own state is represented using:

- **Global position** - where the bot is on the map, allowing it to build and memorize a representation of the map
- **Pitch and yaw** - the bot's orientation within the game-world coordinate system, allowing it to know which direction it is facing
  - **Roll** is omitted because it is always `0` for an FPS camera
- **Velocity (Forward, Right, Up)** - local velocity components
- **Status information**
  - Is airborne
  - Is ducking
  - Is reloading
  - Current health
  - Current ammo in the clip

## Enemy Observation

The visual information of enemies is represented using:

- **Is Valid** - indicates whether this enemy is still considered a valid target. Once visual contact with the enemy is lost, the target remains valid for up to **90 ticks**
- **Is Visible** - indicates whether the enemy is currently visible on screen, based on the geometric visibility test
- **Is Immune** - indicates whether the enemy is currently immune to damage. Newly spawned players have a short period of damage immunity
- **Proximity Score** - represents how close the enemy is to the player
- **Target Delta Pitch and Yaw** - describes where the selected target point is relative to the player's current aim direction
- **Memory Confidence** - represents how confident we are in the enemy's remembered position after it has disappeared from view. It is normalized to [0.0, 1.0] and decreases linearly with the number of ticks since the enemy was last seen

### Enemy Observation Slots

The model has a fixed budget of **5 enemy observation slots**. Since the game can contain more than five potential enemies, the observation system needs to decide which enemies are most important to keep.

The slots are therefore treated as a **priority queue** rather than simply storing the first five enemies encountered.

The priority is based primarily on:

1. Whether the enemy is still a valid target
2. Whether the enemy is currently visible
3. How close the enemy is to the player's current aim
4. For enemies that are no longer visible, how recently they were last seen

This ensures that the model sees the most immediately relevant enemies first.

### Visual sensor

The game updates **64 times per second**, so the bot is designed to make decisions at the same frequency.

Feeding a rendered game frame into a vision model at 64 FPS would be computationally too expensive. Instead, the visual representation of enemies is constructed using **ray casting** and the **view-projection matrix**, which is derived from the player's view angles.

In **CS2**, a player model (or more precisely, its hitboxes) consists of **19 3D capsules (spherocylinders)**.

For this task, the relevant visual information is relatively structured. The bot mainly needs to know:

- Is an enemy inside the camera's field of view?
- Which parts of the enemy are visible?
- How much of the enemy is occluded?
- Where is the visible portion of the enemy?
- Which body hitbox should be prioritized?

Rays are cast toward selected points on the capsule's surface.

To keep the computational cost low, these points are selected only along the **projected silhouette** of the capsule rather than sampling the entire shape.

This produces a compact visual representation of enemy players without requiring rendered frames or a computationally expensive vision model.

### Camera Projection

The first step is constructing a view-projection matrix from the player's:

- World-space camera position
- Pitch
- Yaw
- Horizontal field of view
- Screen dimensions

The camera orientation is represented by three orthogonal basis vectors:

```text
Forward
Right
Up
```

These vectors transform world-space positions into camera space.

The projection then applies the horizontal and vertical FOV scaling and performs the perspective divide.

```text
World position -> Camera space -> Perspective projection -> Clip space -> Perspective divide -> Screen position
```

This allows arbitrary points on an enemy's 3D hitboxes to be tested against the player's camera.

### Capsule Representation

Each enemy is represented by **19 capsule hitboxes**.

A capsule can be thought of as a cylinder with a hemispherical end cap at each end.

Each capsule is defined by:

- Two end-cap centers
- A capsule axis
- A radius

Instead of sampling the entire 3D surface, the algorithm asks:

> **Which points on the capsule form its apparent boundary from the current camera position?**

These points form the capsule's **view-dependent silhouette**.

### Sampling the Projected Silhouette

This is the main optimization.

A naive approach could densely sample the entire capsule surface. Most of these points would be unnecessary.

From a particular camera position, the outer boundary of a convex object determines its projected extent. Therefore, instead of sampling the entire surface, the algorithm constructs a sparse approximation of the capsule's **camera-dependent silhouette**.

The silhouette consists of four components:

1. Top spherical-cap arc
2. Left connecting line
3. Bottom spherical-cap arc
4. Right connecting line

Only these points on these lines/curves are subsequently considered for visibility testing.

With the current parameters:

```cpp
arcPoints  = 7;
linePoints = 4;
```

Each capsule is represented by only a small number of carefully chosen points rather than a dense surface mesh.

### Visibility Testing

Each silhouette sample goes through two tests.

#### 1. Is the point inside the camera view?

The 3D point is transformed using the view-projection matrix.

If it projects outside the screen, it is discarded.

There is no reason to perform an expensive visibility ray-cast for a point that isn't even inside the camera's view.

#### 2. Is the point actually visible?

Only the points inside the field of view is tested. Each candidate point is passed to a ray-cast from the camera to the point.

Only samples for which the ray reaches the target without hitting an occluding object are considered visible.

### Estimating the Visible Target Position

Once visible samples have been found, their world-space positions are accumulated.

The current implementation calculates their arithmetic mean:

```cpp
target = sum(visiblePoints) / visiblePointCount;
```

This produces an estimate of the **center of the visible portion of the prioritized hitbox**. This makes the target point dependent on the actual visible geometry.

### Hitbox Prioritization

The character is represented by 19 hitboxes, which are evaluated in a predefined priority order based on their importance for targeting. The system prioritizes head hitboxes first, followed by torso hitboxes, then arms, and finally legs.

This ordering allows the observation system to identify the most relevant visible target without having to process every hitbox once a suitable target has already been found.

For each hitbox:

1. Generate its silhouette samples.
2. Project the samples into screen space.
3. Perform visibility ray-casts.
4. If at least one sample is visible, calculate the visible center.
5. Stop processing lower-priority hitboxes.

This early termination is another computational optimization.

If a high-priority hitbox is visible, there is no need to perform visibility tests for all remaining hitboxes.

### Limitations

#### Accuracy

This approach deliberately trades some accuracy for computational efficiency.

The most important limitation is that the silhouette is sampled discretely. A very small visible region can fall between sample points.

If no sample lands inside that region, the hitbox may be classified as invisible even though a small portion is technically visible.

Similarly, the estimated visible center is only an approximation of the true center of the visible surface.

The approach also assumes that the capsule hitboxes provide a sufficiently good approximation of the character's visible geometry.

These are intentional trade-offs. The goal is not pixel-perfect visibility reconstruction, but a sufficiently accurate geometric observation that can be evaluated at high frequency.

#### Target Point Selection and Demonstration Ambiguity

The current enemy observation ultimately reduces the visible enemy to a single 3D target point that represents the point the agent should aim at.

For example, when the entire enemy is visible, the selected target may be the center of the head. If the head is not visible but another hitbox is exposed, the system can fall back to a visible hitbox according to the configured priority.

This works well when the desired behavior is explicitly defined as "aim at the best available hitbox."

However, there is an important complication when training from human demonstrations.

The imitation-learning data comes from real players, and human players do not necessarily aim at the same point that the geometric target-selection system considers optimal.

For example, suppose an enemy is completely visible. The current observation might represent this enemy using only the head-center point.

A human player, however, may be aiming at the torso. Both behaviors are valid demonstrations of attacking the same enemy, but the observation does not currently distinguish them.

From the model's perspective, the same enemy state can therefore correspond to different human actions.

With the same enemy observation player might aim at head or torso. This may introduce ambiguity into the imitation-learning target.

One possible solution is to provide the model with two target points instead of one:

**1. Best Aim Point**

Representing the geometrically preferred point to aim at, such as the center of the head.

**2. Visible Center of Mass**

A second point could be computed from the all the visible samples. This would represent the center of the currently visible portion of the enemy.

Currently, ray-casting stops as soon as a suitable target hitbox is found. Testing all sampled points for visibility would therefore introduce some additional computational overhead. However, since each hitbox is represented by only a small number of silhouette points, the total number of additional ray casts remains relatively low, making the added cost potentially negligible in practice.

This additional point will give the model information about where the visible mass of the enemy is, independently of the predefined optimal aim point. The model can then learn the relationship between the two points and the demonstrated behavior rather than being forced to infer the distinction from a single target coordinate.

## Damage Observation

The damage observation provides the model with short-term information about **recent damage received from enemies**. It acts as a form of directional feedback: not only does the model know that it was hit, but also approximately **where the damage came from** and **how recently it happened**.

Each damage event is represented using:

- **Is Valid** - indicates whether this entry contains a real damage event. It is `1.0` when the player has recently been hit and `0.0` when the entry is unused/padding
- **Damage Delta Pitch / Yaw** - describes the direction the damage came from relative to the player's current view direction
- **Damage Intensity** - represents how recently the damage occurred. It starts at 1.0 when the player is hit and linearly decays to 0.0 over 30 ticks

The model has a fixed budget of **2 damage observation slots**. Since multiple enemies can potentially damage the player over time, the system cannot keep an unlimited history of incoming damage.

Instead, the two slots act as a short-term memory of the **most relevant recent damage sources**.

## Temporal Context - Giving the Model Momentum and a Very Short-Term Memory

The model does not only receive the current game tick. Instead, each processed frame contains observations from:

- t-16
- t-12
- t-8
- t-4
- t-0 (current tick)

With the game running at 64 ticks per second, these observations cover approximately 250 ms of recent gameplay. Providing several observations over this short time window gives the model information about how the player's state is changing rather than only its instantaneous state.

This temporal context is particularly useful for learning movement and aiming behavior. For example, the model can observe whether the player has been moving consistently in a particular direction or whether the camera has been turning over several consecutive ticks. This helps it learn to maintain momentum and commit to movement or turning actions instead of repeatedly changing direction or oscillating between opposing inputs.

In addition to this explicit temporal context, the enemy observation system provides a longer form of short-term visual memory. When an enemy is no longer visible, its observation can remain valid for up to 90 ticks, corresponding to approximately 1.4 seconds. The associated memory confidence decreases over time, allowing the model to distinguish between a recently observed enemy and one whose position has become increasingly uncertain.

This gives the model a small amount of memory without requiring a recurrent model or a large history of past observations. Although it is not enough to learn complex long-term behavior, it may be sufficient for learning local navigation patterns, maintaining movement, tracking recently observed opponents, and adjusting aim based on their recent positions.

# Training the Model

Each training sample consists of:

- A 316-dimensional observation vector
- A 9-dimensional action vector recorded from a human player

The observation vector contains:

- Self observations
- Enemy observations
- Damage observations
- Temporal context from previous ticks

The target action vector contains:

- Delta pitch
- Delta yaw
- Forward/backward movement
- Left/right movement
- Shoot
- Jump
- Crouch
- Reload
- Walk

The goal of training is to learn a function that maps observations directly to the actions that a human player performed in the same situation.

## Network Architecture

The current implementation uses a fully connected multilayer perceptron (MLP).

```text
316
 │
 v
Linear(316 → 512)
ReLU
LayerNorm
 │
 v
Linear(512 → 512)
ReLU
LayerNorm
 │
 v
Linear(512 → 256)
ReLU
 │
 v
Linear(256 → 9)
```

The network is intentionally simple. The observation space is already highly structured and contains geometric information extracted directly from the game state, making a large vision model unnecessary.

## Loss Function

The model predicts both continuous and binary actions.

### Continuous Actions

The first four outputs represent:

- Delta pitch
- Delta yaw
- Forward/backward movement
- Left/right movement

These outputs are trained using Mean Squared Error (MSE).

Lcontinuous = MSE(predicted, target)

### Binary Actions

The remaining outputs represent:

- Shoot
- Jump
- Crouch
- Reload
- Walk

These outputs are trained using Binary Cross Entropy with Logits.

Lbinary = BCEWithLogits(predicted, target)

The total loss is the sum of both components:

Ltotal = Lcontinuous + Lbinary

This allows the model to learn both smooth continuous aiming behavior and discrete button presses within a single network.

### Dataset Loading

Training data is stored as a binary file and accessed through a memory-mapped array. This allows datasets containing millions of game ticks to be streamed directly from disk without loading the entire dataset into memory.

The dataset is split into training and validation subsets. During training, the model is optimized on the training set while validation loss is monitored on unseen samples to estimate generalization performance.

### Optimization

The network is trained using the Adam optimizer with a learning rate of 1e-4.

Training proceeds in mini-batches, and after each epoch the model is evaluated on the validation set.

The model producing the lowest validation loss is selected for deployment and exported to ONNX for real-time inference inside CS2.

# Model Inference and Game Integration

Once trained, the model is exported to the ONNX format and loaded directly into the CS2 integration layer using ONNX Runtime. During gameplay, the same observation pipeline used during data collection is executed in real time.

At every game tick, the system constructs:

- The current self observation
- Up to five enemy observations
- Up to two damage observations
- Four historical observations from previous ticks

These observations are flattened into a fixed-size input vector containing 316 features, matching the format used during training. The input tensor is then passed to the neural network, which produces 9 action outputs.

### Predicted Actions

The model predicts the same action representation that was recorded from human demonstrations:

| Output      | Description                 |
| ----------- | --------------------------- |
| Delta Pitch | Vertical mouse movement     |
| Delta Yaw   | Horizontal mouse movement   |
| Move X      | Forward / backward movement |
| Move Y      | Left / right movement       |
| Shoot       | Left mouse button           |
| Jump        | Space                       |
| Crouch      | Ctrl                        |
| Reload      | R                           |
| Walk        | Shift                       |

The first two outputs are continuous values representing camera movement. During preprocessing, human mouse movements were normalized using a non-linear scaling function. During inference, the inverse transformation is applied to recover an approximate mouse movement in degrees.

The remaining outputs are treated as binary actions. The network produces logits, which are converted into probabilities using a sigmoid function. Actions whose probability exceeds 0.5 are considered active for the current tick.

### Real-Time Execution

The game runs at 64 ticks per second, and inference is performed at the same frequency. For every tick:

1. Read the current game state.
2. Build the observation vector.
3. Run a forward pass through the neural network.
4. Convert the predicted outputs into game inputs.
5. Apply the inputs for the next tick.

This creates a closed feedback loop in which the model continuously observes the game state, predicts actions, and receives a new observation resulting from those actions.

### State Representation During Inference

An important property of the system is that the model receives exactly the same type of information during inference as it received during training. No additional information is provided that would be unavailable to a human player.

Enemy observations are generated from the geometric visibility system and short-term enemy memory described earlier. Damage observations provide directional feedback about recently received damage. Together with the temporal observation history, this gives the model enough context to react to visible opponents, continue ongoing movement, track recently observed enemies, and respond to incoming attacks.

### Current Limitations

The model operates purely as a reactive policy. It predicts the next action directly from the current observation and short temporal history. It does not maintain an explicit long-term memory, perform planning, or reason about future game states.

As a result, the model is primarily expected to learn behaviors such as:

- Aiming at visible enemies
- Tracking moving targets
- Navigating the map locally
- Maintaining movement momentum
- Reacting to recent damage
- Following opponents that have recently left the field of view

More complex behaviors that require longer-term reasoning, strategic planning, or understanding objectives beyond immediate combat would likely require additional memory mechanisms, recurrent architectures, or more advanced reinforcement-learning approaches.

# Future Work and Improvements

The current project focuses on learning basic movement and aiming behavior in CS2 Deathmatch. There are several directions in which the system could be improved and extended.

### Improving the Observation Representation

The current visual enemy observation represents a target primarily using a single geometrically selected aim point. A possible improvement would be to provide additional information about the visible portion of the enemy, such as a second visible center-of-mass point alongside the preferred aim point.

This could reduce ambiguity in the demonstrations. Human players may aim at different parts of an enemy even when the underlying game state is identical. Providing both points would give the model more information about the available target geometry instead of forcing it to infer this distinction from a single target coordinate.

The observation system could also be extended with additional information such as weapon state, current weapon type, and more detailed information about nearby players.

### Adding Sound Observation

Currently, the bot is effectively deaf. The human demonstrations used for training contain decisions that are influenced by sounds, but the model has no information about those sounds or their sources.

For example, a human player might hear an enemy approaching from around a corner and stop moving or begin aiming toward the corridor before the enemy becomes visible. From the model's perspective, there is no obvious reason for this change in behavior because the enemy is not yet present in its visual observation.

Adding a sound observation would allow the model to distinguish between actions caused by visible information and actions caused by audio cues. The observation could contain information such as the direction and type of recently heard sounds, together with a short decay over time.

This would provide the model with an additional source of information that was available to the human demonstrator, making the training data more consistent with the information actually used to produce the demonstrated actions. It could also make the resulting policy more robust in situations where enemies are temporarily hidden but can still be detected through sound.

### Improving the Training Process

The current model uses a relatively simple MLP trained with a combination of regression and binary classification losses. The training pipeline could be improved by experimenting with:

- Different network architectures
- Better weighting between continuous and binary losses
- Class weighting for rare actions such as jumping and reloading
- More robust regression losses for mouse movement
- Learning-rate scheduling
- More carefully separated training and validation datasets

Another important improvement would be evaluating the model using metrics specific to each action rather than relying only on the combined training loss.

### Improving Temporal Modeling

The current approach provides a short history of observations to the MLP rather than using an explicit recurrent model.

A future version could experiment with architectures designed specifically for sequential data, such as recurrent networks or attention-based models. This could allow the agent to learn temporal relationships more directly and potentially maintain longer-term context.

However, this would also increase the computational complexity of real-time inference.

### Extending Beyond Deathmatch

The current project deliberately focuses on Deathmatch because it provides a relatively simple environment for learning movement, aiming, and combat behavior.

A natural next step would be to extend the system to the main competitive game modes. This would require significantly richer observations and a model capable of handling:

- Team coordination
- Round objectives
- Economy management
- Weapon and utility selection
- Teammate positions and health
- Enemy information that is only partially observable
- Longer-term strategic decisions

This would represent a substantially more difficult imitation-learning problem than the current Deathmatch task.

### Evaluating the Agent in the Game

Another important area of future work is developing better evaluation methods. Validation loss alone does not necessarily indicate how well the trained policy actually performs in the game.

The agent could instead be evaluated using metrics such as:

- Kill/death ratio
- Accuracy
- Damage dealt
- Survival time
- Movement behavior
- Target-tracking accuracy
- Performance across different maps and sessions

Comparing these metrics against the original human demonstrations would provide a more meaningful measure of whether the learned policy successfully reproduces useful gameplay behavior.

### Exploring More Advanced Learning Methods

Behavioral cloning provides a straightforward way to learn from demonstrations, but it also has a fundamental limitation: the model can only learn behaviors represented in the training data.

Future work could combine behavioral cloning with other approaches, such as reinforcement learning or additional fine-tuning from the agent's own gameplay. This could allow the model to improve behaviors that are difficult to learn purely from demonstrations and potentially correct errors that accumulate during autonomous play.

The overall goal would be to gradually move from reproducing individual human actions toward learning a more robust gameplay policy.
